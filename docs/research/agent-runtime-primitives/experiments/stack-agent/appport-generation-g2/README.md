# AppPort generation G2: can the patched `appport add` produce a bridge Stack-Agent can use?

This record follows `../appport-generation-g1/` (the published generator could not bind) and
`../appport-mcp-m1/` (Stack-Agent consumed the SDK-built Vikunja bridge through MCP). It tests the
second of two independent claims:

1. *Stack-Agent can use AppPort capabilities generically through MCP*: shown in M1.
2. *AppPort can generate a working integration from an existing application*: tested here.

**Answer: not yet, for Vikunja or for any application through the intended MCP path.** The generator
patch is validated and committed. With it, an Express application's routes are bound correctly and
served by `appport dev`. Vikunja stops at the first stage: no HTTP operation is discovered. Two
further blockers are measured or read on a target where discovery works; they would stop any
generated bridge before Stack-Agent could reach it through MCP. No Stack-Agent run against a
generated bridge was possible, so none is reported.

Labels: **measured** (run here), **read** (from code). Nothing was hand-written or repaired in any
generated file, and no MCP workaround was built.

## 1. Generator validation (measured)

Repository `rkendel1/appboundry`, branch `claude/inspiring-shannon-axjqdq`, base `7d530ac`. The patch
changes `packages/cli/src/commands.ts` and adds `packages/cli/test/http-bridge.test.ts`. It is
committed as **`664726d`**, unreleased: no version bump, nothing published.

The patch makes these changes:

* GET and the other methods of one path are kept as separate operations;
* path parameters become required inputs;
* the binding's method is passed through;
* the configured origin is used;
* path parameters are substituted and URL-encoded; query for GET/HEAD/DELETE, JSON body otherwise;
* timeouts apply, and redirects are refused;
* upstream failures are typed errors, never results;
* the `appport/server.ts` that `appport dev` loads is generated.

Review added one fix: an implementation generated by an earlier CLI calls the runtime without a
method, and `appport add` preserves it as developer-owned. The old error told the developer to
regenerate, which cannot fix it; the error now names the actual fix, and a test covers it.

## 2. Vikunja through the patched generator (measured)

Target: `rkendel1/vikunja` at **`394b5f3`**, the parent of the bridge commit. `851a9da` adds only
`appport-bridge/` and its CI workflow, so the Vikunja server is the one M1 used. The full tree
(2,293 files) was exported to a disposable directory with `git archive`. CLI:
`packages/cli/dist/bin.js` built from `664726d`.

| Stage | Result | Evidence |
| --- | --- | --- |
| Source discovery | **fails: 0 HTTP operations.** 6 candidates, all Electron IPC channels in `desktop/` | `artifacts/vikunja/discovery.txt` (the CLI's own `discoverCapabilityCandidates`, via `artifacts/discover.mjs`) |
| Repository understanding | `appport app`: "Node.js / TypeScript repository"; it lists `vikunja-desktop` and `vikunja-frontend`, not the Go server; then stops at the interactive prompt (exit 13) | `artifacts/vikunja/appport-app.txt` |
| Capability generation | `appport add --capability tasks.get` exits 0 but writes a contract capability with an empty open input schema and a stub that throws `Implement tasks.get@1`. No `appport.bridge.json`, no binding, no runtime bridge | `artifacts/vikunja/appboundry.contract.json`, `implementation.index.ts`, `appport-add.txt` |
| Contract correctness, runnable bridge, MCP, authority, interpretation, verification | **not reached** | — |

**Smallest reproduction.** The analyzer's HTTP patterns (`commands.ts`, `discoverCapabilityCandidates`)
are:

* Express-style `(app|router|server).(get|post|put|patch|delete)("…")`, lower case;
* Node `request.method` and `url.pathname` comparisons;
* Go `HandleFunc(` / `Handle(` / `RequestURI ==`, which only feed live probing.

Vikunja registers its v1 routes with Echo's receiver form, for example
`a.GET("/tasks/:projecttask", taskHandler.ReadOneWeb)` (`pkg/routes/routes.go:710`), and its v2 API
through `huma.Register` (`pkg/routes/api/v2/huma.go:161`). Neither form matches.
`artifacts/repro/echo/main.go` (one Echo route) yields 0 candidates. For comparison,
`artifacts/repro/handlefunc/main.go` also yields 0, because a `HandleFunc` route becomes a candidate
only when a live origin answers it. `add` has no supported way to declare a route that
discovery missed: it takes capability names only.

Per the task's rules, the Vikunja comparison stops here. No analyzer change was made: general parser
improvements are out of scope.

## 5. Remaining blockers, by layer

| Layer | Blocker | Applies to |
| --- | --- | --- |
| Source analysis | Go Echo receiver routes (`a.GET("/…", h)`) and huma registrations are not recognized; repository understanding picks the Node sub-projects | Vikunja |
| Capability generation | `add` cannot declare an HTTP binding for a route discovery missed | any missed route |
| Contract | one scope per name prefix, so read and write cannot be granted apart; no `effect`, no `verify`; output is any JSON | every generated bridge |
| Runtime and authority | no forwarding of the caller's application credential | applications that authorize per caller |
| MCP transport | MCP exists only on the host, for packaged WASM; a TypeScript bridge cannot be packaged, and `appport dev` has no MCP endpoint | every generated bridge |
| Stack-Agent | none new. The generic MCP source is unchanged (M1); its limits (replay only, stateless replay, recording coverage) remain | — |

## 6. Next smallest justified step

Serve the generated application over MCP from `appport dev`: mount the existing `@appport/mcp`
`createMcpHandler` on the application `server.ts` already exports, with the host's own controls
(`APPPORT_MCP_TOKEN`, scopes from `APPPORT_MCP_SCOPES`). This is a single change in
`packages/cli` that reuses existing packages. It would let the invoice desk be tested end to end
with M1's unchanged Stack-Agent source and record and replay. That separates the MCP layer from the
contract and authority gaps, and from Vikunja's discovery gap, which each need their own change
(per-operation scopes and credential forwarding; Echo and huma route recognition).
